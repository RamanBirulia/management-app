## Реализовано

- All Logs фильтруется по нескольким типам, статусам, людям, проектам и диапазону дат.
- Между группами применяется AND, внутри одной группы — OR; правило подписано в интерфейсе.
- Активные фильтры и номер страницы сохраняются в URL query params, поэтому представление можно открыть на другом устройстве.
- Даты интерпретируются в `Europe/Tallinn`, включая переход между зимним и летним временем.
- Страницы `/people/:id` и `/projects/:id` переиспользуют журнал с обязательным контекстным фильтром.
- Имена в справочнике ведут на соответствующие контекстные страницы; архивные записи доступны по прямому URL.
- Реализованы отдельные loading, empty и error states для контекстных и отфильтрованных представлений.
- Компоновка фильтров и контекстных страниц адаптируется для desktop и tablet.

## API

`GET /api/logs` принимает повторяемые параметры:

- `type=decision|task|question`;
- `status=open|unassigned|done|cancelled|resolved`;
- `person=<uuid>`;
- `project=<uuid>`;
- `from=YYYY-MM-DD`, `to=YYYY-MM-DD`;
- `page=<number>`.

Добавлены `GET /api/people/:id` и `GET /api/projects/:id` для прямых контекстных страниц.

## Эксплуатация

- Опубликованная версия использует Sites-managed D1 и owner-only access; ошибки запросов и uptime доступны в журнале Worker/Sites без записи содержимого логов.
- Схема и все миграции версионируются в Git и входят в каждый deployment artifact.
- PostgreSQL production-like контур сохраняет health endpoints и документированный volume. Автоматизированный off-site backup/restore остаётся отдельной инфраструктурной задачей перед переносом реальных данных на выделенную машину.

## Проверено

- Multi-select разбирается как OR внутри группы и очищает неизвестные type/status.
- Границы дат проверены для летнего и зимнего времени Tallinn.
- Фильтр использует структурированные immutable IDs, поэтому переименование не меняет состав результатов.
- Root и контекстные routes компилируются и отвечают без ошибки.
- Typecheck, lint, API/domain tests и production build проходят.
