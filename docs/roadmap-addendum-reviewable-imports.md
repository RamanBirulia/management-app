# Roadmap Addendum — Reviewable Imports & Jira Intake

- Статус: **запланирован**
- Рабочее название: **Release 5.1 — Reviewable Imports & Jira Intake**
- Положение в roadmap: после Release 5 (Work Items), до следующих этапов планирования

Этот этап добавляет безопасный путь из внешнего текста и систем управления задачами в Management Log. Главный принцип: AI и импорт создают только предложения. Decision, Task, Question или Work Item становятся каноническими данными только после явного подтверждения человеком.

## Результат релиза

Пользователь может передать транскрипт встречи, конспект, структурированный файл или выгрузку внешней системы, увидеть предложенные решения, задачи и вопросы, а затем принять или отклонить каждый элемент.

## Два слоя решения

### 1. Универсальный reviewable import

- Завести сущности `ImportBatch` и `ImportSuggestion`.
- Поддержать предложения типов Decision, Task и Question; после Release 5 — связь или преобразование Task в Work Item.
- Для Work Item позволить предложить project, workflow stage, Sprint и место рядом с существующим rank, но применять их только после review.
- Принимать единый версионированный формат импорта независимо от источника.
- Источниками первой версии могут быть транскрипт Granola, вставленный plain text, JSON и ручная CSV/JSON-выгрузка.
- Сохранять происхождение предложения: тип источника, внешний идентификатор или URL при наличии, время импорта и идентификатор batch.
- Проверять входные данные на сервере. Результат AI считается недоверенным содержимым, а текст транскрипта — данными, не инструкциями приложению.

### 2. Jira intake поверх общего контракта

- Начать с управляемого ручного импорта Jira: экспорт JSON/CSV или подготовленный набор задач.
- Хранить `source_system`, Jira issue key, внешний URL и другие стабильные идентификаторы для дедупликации.
- Повторный импорт той же задачи не должен молча создавать дубликат.
- API/OAuth, периодическую синхронизацию и webhooks проектировать только после решения, какая система является source of truth и какие поля синхронизируются в каждую сторону.
- До этого решения синхронизация остаётся явной и запускается вручную.

## Skill для подготовки предложений

В рамках реализации нужен отдельный project skill, предварительный путь: `skills/management-log-import/SKILL.md`.

Skill получает длинный текст, конспект или транскрипт встречи и формирует структурированный batch предложений:

- решения, которые стоит зафиксировать;
- задачи с возможными assignee, due date и связями;
- открытые вопросы;
- упоминания людей и проектов;
- короткое обоснование или ссылка на фрагмент исходного текста.

Skill не пишет напрямую в журнал. Его результат проходит schema validation и открывается в интерфейсе импорта для человеческой проверки. Неоднозначные люди, проекты, даты и типы записей остаются явно неразрешёнными, а не угадываются скрыто.

## Import UI и review flow

1. Пользователь нажимает `Импорт` и вставляет подготовленный текст/JSON либо выбирает поддерживаемый файл.
2. Приложение создаёт batch и показывает список предложений, сгруппированный по Decision, Task и Question.
3. Каждая карточка отмечена как `Предложение · требует проверки` и визуально отличается от обычной записи.
4. До решения вместо обычного меню `Изменить / Удалить` показываются действия `Да` и `Нет` (`Approve / Reject`).
5. `Да` создаёт каноническую запись ровно один раз и сохраняет связь с исходным предложением.
6. `Нет` отклоняет предложение и не создаёт запись в журнале.
7. Желательно позволить исправить текст и связи до подтверждения; точный UX фиксируется перед реализацией.

Все предложения по умолчанию не подтверждены. Batch не должен иметь действие, которое незаметно подтверждает всё содержимое без review.

## Надёжность и приватность

- Использовать idempotency key или content hash для безопасного повтора импорта.
- Частичная ошибка не должна оставлять непонятное состояние: обработка возобновляется без повторного создания уже подтверждённых записей.
- Исходный транскрипт по умолчанию не хранить дольше, чем нужно для review, либо дать явное управление сроком хранения.
- Не отправлять управленческие данные сторонним аналитическим сервисам.
- Хранить минимальный audit trail: кто и когда импортировал, подтвердил или отклонил предложение.

## Критерии приёмки

- Транскрипт преобразуется в валидный batch, но до подтверждения в каноническом журнале нет новых записей.
- Подтверждение одного предложения создаёт запись нужного типа и переносит структурированные связи.
- Отклонение не создаёт каноническую запись.
- Повтор одного batch не дублирует предложения и подтверждённые записи.
- Повторный импорт Jira issue с тем же key распознаётся как уже известный.
- Неоднозначное упоминание требует выбора Person/Team/Project.
- После частичного сбоя импорт можно безопасно продолжить.

## Решения, которые нужно принять до разработки

- Разбирать ли raw text внутри сайта с использованием AI или первая версия принимает только результат project skill.
- Какой формат является публичным versioned import contract.
- Jira или Management Log является source of truth для статуса, assignee, due date и текста задачи.
- Нужна ли двусторонняя синхронизация или достаточно повторяемого intake из Jira.
- Хранить ли отклонённые предложения для аудита и как долго хранить исходные транскрипты.

## Не входит в первую версию

- Автоматическое подтверждение AI-предложений.
- Фоновая двусторонняя синхронизация Jira.
- Автоматическое разрешение неоднозначных людей, команд и проектов.
- Полная поддержка всех полей и workflow Jira.
- Импорт без provenance и защиты от дубликатов.
